# 0.2.0 implementation review

## Product boundary

The package accepts a completed article and owns execution from a durable job through external publication, public URL discovery, and continuing liveness verification. It does not generate, rewrite, plan, score, or approve content.

## Key decisions

- A job is the only lifecycle aggregate. Earlier parallel browser-job, schedule, and ledger models were removed.
- External publication is protected by an immutable content hash, a caller-stable job ID, an idempotency key, a worker lease, and a platform write lock.
- Ambiguous writes move to read-only verification. They are never automatically resubmitted.
- A public URL is provisional. The engine records 24-hour and 72-hour survival, marks stable publication, and continues daily checks so later removal can still be detected.
- Official platform rules are evidence-backed transport constraints, not editorial preferences.
- Credentials stay outside repositories and authorization records. Security challenges always require human takeover.

## Remaining operator acceptance

Automated tests emulate first-party WeChat API responses and prove the executor's request/state flow without using a real account. Before a production deployment, an authorized operator must configure a verified account, record acceptance, publish one non-sensitive article, confirm the returned public URL, and allow the worker to record the 24-hour and 72-hour observations. This is an environment acceptance step, not missing engine code.
